## 一、为什么要单独看 daily_stock_data

其他项目大多在“分析层”发力：多 Agent、评分、回测、报告、交易执行。`daily_stock_data` 的价值在更靠下的位置：它把数据采集这件事做成了可运行、可迁移、可开源的底座。tickflow-stock-panel 则补上另一种形态：数据已经不只是采集产物，而是一个可交互量化工作台的运行底座。

这类能力经常被低估，但所有分析系统最后都会被它卡住：

- 数据从哪里来；
- 失败后怎么补；
- 本地试用和长期运行是否同一套代码；
- 下游到底依赖哪些字段；
- 开源时有没有把私有路径、密钥、数据 dump 一起带出去。

## 二、双后端存储模式

`storage_common.py` 用一个环境变量决定存储模式：

```env
STORAGE_BACKEND=csv       # 默认，开箱即用
STORAGE_BACKEND=postgres  # 长期运行
STORAGE_BACKEND=both      # 双写迁移/对账
```

关键不是“支持两种存储”，而是每种模式的职责清楚：

| 模式 | 适合场景 | 注意点 |
|------|----------|--------|
| `csv` | 初次试用、日线、基础资料、小规模研究 | 读全表再写，不适合长期高频 |
| `postgres` | 5 分钟线、逐笔、F10、快照长期运行 | 需要 schema 和索引维护 |
| `both` | 从 CSV 迁移到 PG、对账、灰度验证 | 要防止双写失败语义不一致 |

借鉴原则：不要让用户一开始就装数据库；也不要让项目永远停在 CSV 脚本阶段。

## 三、tickflow-stock-panel 的 Parquet 本地数据湖

tickflow-stock-panel 没有把 DuckDB 当主数据库，也没有让 React 页面直接依赖一堆 CSV。它的结构更像一个轻量本地数据湖：

```text
Parquet 分区目录  = 磁盘真相
DuckDB in-memory  = 冷查询/统计/视图层
Polars scan/cache = 热路径/指标计算/策略筛选
```

### 3.1 DataStore 目录就是数据契约

`DataStore` 启动时创建固定目录，包括：

| 目录 | 用途 |
|------|------|
| `kline_daily/` | 日 K 原始数据 |
| `kline_daily_enriched/` | enriched 窄表分区 |
| `kline_minute/` | 分钟 K |
| `financials/` | 财务 metrics、利润表、资产负债表、现金流 |
| `ext_data/` | 用户扩展分析表 |
| `user_data/` | 监控规则、自定义信号、偏好 |
| `depth5/` | 五档盘口旁路数据 |

目录名不是实现细节，而是下游 API、调度器、策略引擎和 UI 共同依赖的数据契约。

### 3.2 窄表 enriched，宽表运行时

`kline_daily_enriched` 落盘时只存稳定字段：OHLCV、raw price、换手率、连板数等。MA、MACD、BOLL、KDJ、RSI、自定义信号等指标在读取时由 Polars 即时计算。

这适合早期量化产品：指标公式经常变，若每次都迁移全量宽表，维护成本会快速失控。窄表让磁盘契约稳定，宽表留给运行时。

### 3.3 DuckDB 只做视图，不做真相

DuckDB 连接是 `:memory:`，所有视图从 Parquet glob 注册。好处是：

1. 迁移和备份只需要处理文件目录；
2. 查询层坏了不影响磁盘数据；
3. 对用户来说部署成本比完整数据库低。

借鉴原则：如果项目是个人量化、桌面版或自托管小系统，Parquet + DuckDB + Polars 往往比“先上数据库”更轻、更稳。

### 3.4 时序数据库的引入边界

时序数据库不是数据湖的替代品。`hermes-data` 默认把 immutable raw 和标准化历史数据保存为 Parquet，DuckDB 负责研究和批量查询，PostgreSQL 负责目录、权限和运行态；只有近期 bars/ticks 需要持续在线查询、连续聚合或较高并发时，才增加 TimescaleDB 作为可重建的热数据副本。全量 Tick、深度盘口和大规模历史聚合应在实际查询压力出现后再评估 ClickHouse。

```text
Go collector -> canonical normalizer -> Parquet/对象存储（事实源）
                                      -> DuckDB（分析查询）
                                      -> TimescaleDB（可选热数据）
                                      -> Valkey（最新状态/缓存）
```

### 3.5 RisingWave 的引入边界

RisingWave 只作为实时流计算层，不作为主数据存储、历史数据湖或批量编排器。第一阶段的实时行情如果只是采集、标准化、推送和缓存，Go collector、消息队列和 Valkey 足够；当需要跨 provider 的事件时间 Join、窗口聚合、实时因子、持续物化视图或复杂告警时，再引入 RisingWave。引入后仍应把原始事件和标准化结果落到 Parquet，RisingWave 的状态和物化结果视为可重建副本。

```text
Go Adapter -> Kafka/Redpanda -> RisingWave（可选实时计算） -> API/WS/Valkey
                                      └---------------------> Parquet 数据湖
```

### 3.6 查询与写入实现边界

当前 `stockdb` kernel 的 `start/end` 过滤是在 Arrow 读入后由 Polars 执行，日期 predicate 没有在 kernel 路径下推到文件读取阶段；需要大范围过滤时，应先按分区目录选择文件，或直接使用 DuckDB 对 Parquet 数据集做扫描。跨大量标的、跨目录和宽时间范围分析优先走 DuckDB，Polars kernel 适合单文件、少量标的和局部转换。

`generic_upsert` 会读取旧表、合并去重、排序后整表重写（见 `src/stockdb/store/table_spec.py:43`），因此只能用于低频表、修复和小范围校正。高频行情应采用 append-only 分区、微批文件、manifest/commit 标记和后台 compaction；去重和修订通过分区级任务处理，不能在每条行情到达时整表 upsert。

分钟聚合当前会先读取完整时间窗口再执行 resample。采集系统应按完整窗口或微批触发聚合，使用 watermark 处理迟到事件，并将聚合结果作为可重建的派生数据，不把逐 tick 全窗口重算放进实时热路径。

## 四、CSV 也要有事务感

`daily_stock_data` 的 CSV 操作有三个工程细节：

| 函数 | 语义 | 借鉴点 |
|------|------|--------|
| `write_csv_table` | 临时文件写完后 `os.replace()` | 避免中断产生半截 CSV |
| `append_upsert_csv` | 拼接旧数据和新数据，按 key 去重保留最新 | 日线/基础资料的最小可靠 upsert |
| `replace_csv_slice` | 只替换某个 symbol 的日期窗口 | 分钟线修复不影响其他标的 |

这比“直接 `df.to_csv(path)`”多不了几行，但稳定性差别很大。

## 五、采集任务的包装器模式

所有定时任务推荐从 `bin/run_*.sh` 进入：

```
bin/run_daily_sync_batches.sh
bin/run_5min_sync_batches.sh
bin/run_tencent_snapshots.sh
bin/run_tushare_stock_basic_sync.sh
bin/run_tdx_tick_trades_pm.sh
...
```

包装器统一负责：

- 回到项目根目录；
- 读取 `.env`；
- 创建 `logs/`；
- 设置 `PYTHONPATH=scripts`；
- 调用实际 Python 采集脚本。

这是一种低成本但很有效的“运行层抽象”。Python 脚本不需要知道自己被 cron、手工还是 CI 调用；shell wrapper 也不掺业务逻辑。

## 六、增量同步 + 小窗口修复

日线脚本有一个实用参数：`--repair-days`。

含义：增量同步时不仅补最新缺口，还固定回看最近 N 个交易日，覆盖上游迟到、修订或临时失败。

这个模式适合迁移到：

- 日线行情；
- 资金流；
- 新闻/公告；
- 研报列表；
- 财报摘要。

原则：只追加会漏掉修订，全量刷新又太重。小窗口修复是更稳的默认策略。

## 七、统一快照表 + 当前态表

腾讯快照采集拆出两个表：

| 表 | 作用 |
|----|------|
| `quote_snapshots_unified` | 每次采集的时间序列快照 |
| `latest_tick` | 每个 symbol 的最新状态 |

下游使用时，历史分析走快照表，当前行情走 latest 表，不需要在一个大表里既做时序查询又做最新态查询。

可迁移到当前项目：

- `market_snapshots`：行情时间序列；
- `latest_market_state`：最新市场态；
- `latest_agent_run`：每个标的最新分析结果；
- `report_snapshots`：历史报告版本。

## 八、数据契约作为一等文档

`docs/SCHEMAS.md` 把表字段、主键、时间语义和规模边界写清楚。相比代码注释，它有两个优势：

1. Agent/LLM 可以直接读契约，不需要反向解析脚本；
2. 下游项目可以把契约当接口，而不是依赖某个脚本实现。

建议当前项目新增或强化：

```
docs/DATA_CONTRACTS.md
├── 表/文件名
├── 主键/去重键
├── 时间语义和时区
├── 字段单位
├── provider/source/fetched_at
├── 缺失值语义
└── CSV/PG/缓存规模边界
```

## 九、CI 的“隐私泄漏”检查

`daily_stock_data` 的 CI 除了 ruff、编译、pytest、shell syntax，还 grep 私有路径和本地敏感痕迹。

这条对个人项目开源尤其重要。建议当前所有项目加一类检查：

```bash
! grep -RInE '(/home/|/Users/|miniconda|\.config/|dump|private|secret)' .
```

实际项目可维护更精确的 denylist，避免把个人目录、私有数据路径、账号标识、导出语料库路径带进仓库。

## 十一、后两批补充：Agent 工具层也是数据底座

后两批项目提醒我们，数据底座不只有“数据库/文件/数据湖”。当系统给 Agent 使用时，工具调用层本身也是数据底座的一部分，因为下游依赖的是命令输出、response envelope、缓存提示和权限边界。

| 数据层形态 | 代表项目 | 适用数据 | 必须保留的契约 |
|------|---------|---------|---------------|
| JSON CLI | snowball-cli | 雪球行情、财务、F10、社交、基金 | command、args、public/auth、raw JSON、HTTP error |
| Skill Gateway | Privora Examples | 数据资产、持仓、组合 | `skillId`、scope、params、response shape、DEK 状态 |
| Agent Gateway Runtime | QuantDinger | 回测、实验、策略、纸面订单、Agent 调用 | token scope、idempotency key、job_id、audit summary、paper_only |
| Static Snapshot | hhxg-market | 日报、两融、日历、快讯 | date、schema_version、from_cache、最近交易日说明 |
| Local Daemon Cache | magpie | 自选股、提醒、报价缓存 | watchlist、alert_rules、alert_history、quote_cache |
| Skill SQLite Memory | Awesome Finance Skills | 新闻、搜索、股票、信号、引用 | search_cache、search_detail、signals、citation key |
| Desktop Runtime Context | JCP / PanWatch | 股票记忆、持仓上下文、same-day cache | stock memory、portfolio context、budget/cooldown |

### 新原则

- 数据底座要覆盖“怎么被 Agent 调用”，不仅是“数据如何落盘”。
- response shape 要像表结构一样稳定，变更要有版本和迁移说明。

## 十三、Polymarket：盘口、链上事实与解析事实分离

新增源码研究补充了预测市场的数据底座边界：

```text
统一 SDK / CLOB client       -> 市场、订单、账户、盘口 API
real-time-data-client        -> 活动、价格、用户消息 WebSocket
polymarket-subgraph          -> Conditional Tokens、交易、OI、PnL、活动
resolution-subgraph         -> UMA/CTF resolution、dispute、settlement
go-market-events             -> Polygon RPC 低层事件 watcher
```

这些来源不能互相替代。CLOB 的订单状态需要与 `OrderFilled` 等链上事件对账；resolution 的“已解析”也不等于用户已经完成 redeem。建议为预测市场增加独立的 `market_events`、`resolutions`、`settlements` 和 `position_transfers` 表，并保留 `block_number`、`transaction_hash`、`log_index`、`condition_id`、`token_id` 和 provider/source。

`ctf-exchange-v2`、`uma-ctf-adapter` 和 `neg-risk-ctf-adapter` 是结算契约与状态机的源码证据，不应被当成普通数据 provider；任何执行动作都要经过服务端 ActionGuard 和链上 reconciliation。
- 对含认证或敏感数据的工具，scope/token/DEK/session 是数据契约的一部分。
- 静态快照适合先落地日报类能力，再逐步升级到实时服务。

## 十四、新增项目：Provider、回测与编排分层

本批源码研究把数据底座进一步拆成四个边界：

| 层 | 代表源码 | 应吸收的模式 | 不应承担的职责 |
|---|---|---|---|
| 原始 provider | `openbb`、`akshare` | Provider/Fetcher、主题函数、统一结果、source health | 直接作为事实库或交易信号 |
| 交易连接器 | `ccxt`、`hummingbot` | capability、market cache、connector、order lifecycle | 组合风险和跨市场结算 |
| 研究计算 | `vectorbt`、`nautilus-trader` | 参数广播、records、事件回放、研究/live parity | 用回测结果替代实盘对账 |
| 数据工作流 | `dagster`、`temporal` | asset lineage、materialization、durable job、retry | tick 级行情和低延迟订单路径 |
| 标准化层 | `hermes-data` canonical normalizer + `InstrumentMaster` | 实体解析、字段映射、单位/时区/日历归一化、复权、隔离区和修订追踪 | 覆盖 immutable raw 或强行抹平领域语义 |

因此，采集任务应把 `openbb`/`akshare` 的 DataFrame 或 OBBject 包装成 `ProviderResult`，保存 provider、参数、available_time、raw_hash、schema 和质量状态；`hermes-data` 先保存 immutable raw，再由 canonical normalizer 统一 `instrument_id`、时间、单位、货币、精度和市场日历，清洗失败进入 quarantine。`Dagster` 作为默认控制面负责 raw -> canonical -> quality -> snapshot 的批次、分区回填和质量门；`Temporal` 只保留给需要长时间等待与强恢复语义的业务流程，二者都不取代 Redpanda/streaming。

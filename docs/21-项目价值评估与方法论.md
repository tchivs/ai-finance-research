# 项目价值评估与方法论

> 本文基于各项目 `QUICK-START.md` 与跨项目综合文档快速评估，目的是辅助优先级判断和方案选型。它不是对上游项目生产可用性的最终背书；进入实现前仍应回到对应 `DEEP-ANALYSIS.md` 和固定 commit 证据核对限制、依赖和风险。

## 1. 总体结论

42 个项目反复指向同一个建设顺序：先稳定数据和工具边界，再引入 Agent 编排，最后产品化为工作台、盯盘、报告或交易系统。

```text
数据契约
    -> 工具调用 envelope / scope / audit
        -> 策略、信号、因子资产化
            -> Agent 编排和可回放研究流程
                -> UI 工作台、盯盘、报告、审计
```

最值得优先吸收的不是“更多 Agent”或“自动交易”，而是以下工程纪律：数据契约、工具审计、策略资产化、确定性风控、可回放实验、静态快照、能力拆包和报告可信度展示。

## 2. 价值评级口径

| 评级 | 含义 |
|------|------|
| 高 | 架构或产品闭环强，可迁移价值高，能影响核心建设路线 |
| 中 | 单点能力明确，适合作为模块或局部模式借鉴 |
| 低 | 当前资料中成熟度、适用范围或可迁移价值有限 |

本批项目没有明显“低价值”项目；大多数至少提供一个可迁移模式。评级差异主要来自成熟度、闭环完整度、通用性和当前金融 AI 系统适配度。

### 受限模式参考：FinceptTerminal

`FinceptTerminal` 不进入项目总表或实现候选。它的 DataHub、MCP 注册、Python 子进程桥接和原生工作台分层有模式参考价值，但上游公开仓库采用 AGPL-3.0，并声明商业或内部公司使用需要单独商业许可；公开版也已转为月度维护。只记录其“UI 不直接拉数据、由带 TTL/订阅策略的数据总线统一调度”的设计，不复制代码、依赖或完整桌面终端范围。

## 5. 最佳方法论

### 5.1 数据契约先行

代表项目：`daily-stock-data`、`tickflow-stock-panel`、`agentic-china-data-tooling`、`qlib`

先定义字段、时间语义、来源、缓存、缺失值、schema version，再让 Agent、策略和 UI 使用。金融系统中，数据不稳，后面的 AI 分析、回测和报告都会漂。

### 5.2 工具调用可审计

代表项目：`quantdinger`、`quant-buddy-skill`、`privora-python-examples`、`snowball-cli`

所有 Agent 工具调用都要有 `tool/skillId`、参数、session、版本、scope、response shape、错误码、原始响应摘要。不要让 Agent 自由拼 HTTP 请求或猜接口。

### 5.3 Strategy / Signal 资产化

代表项目：`qlib`、`alphaagent`、`tickflow-stock-panel`、`alpha-evolution-lab`

策略、因子、信号都应该有 DSL/YAML/配置、版本、父子关系、评估指标、回测结果、适用条件，而不是散落在 notebook、脚本或 prompt 里。

### 5.4 Agent 只做判断，规则层做约束

代表项目：`quantdinger`、`ai-hedge-fund`、`panwatch`、`pa-agent`、`lean`

LLM 可以解释、辩论、总结，但仓位、权限、交易边界、预算、冷却、最大损失、`paper_only` 都必须由确定性代码控制。

### 5.5 多 Agent 要有 Moderator

代表项目：`jcp`、`tradingagents-family`、`ai-berkshire`

多 Agent 的价值不是角色数量，而是任务分配、观点冲突、状态保存和裁决过程。先判断意图，再选择专家，再分配每个专家的职责。

### 5.6 研究过程可回放

代表项目：`rd-agent`、`deepfund`、`quant-autoresearch`、`qlib`

保存 hypothesis、输入数据、代码变更、运行结果、反馈、是否接受。这样系统才能长期进化，而不是每次从聊天上下文重新开始。

### 5.7 盯盘是触发系统，不是定时报告

代表项目：`panwatch`、`magpie`、`a-share-watch-butler`

提醒必须有规则、触发历史、冷却、预算、交易时段、test-fire、建议池。否则只是会重复打扰用户的 cron 脚本。

### 5.8 静态快照优先于实时复杂系统

代表项目：`hhxg-market`、`daily-stock-data`、`tickflow-stock-panel`

盘后日报、日历、两融、快讯、市场情绪可以先生成静态 JSON/Parquet，让 Agent 读取稳定结果。不要一开始就追求大规模实时行情。

### 5.9 能力拆成 Skill / MCP / CLI

代表项目：`awesome-finance-skills`、`wudao-mcp`、`joinquant-skill`、`snowball-cli`

把数据、搜索、情绪、预测、报告、策略 lint 分成小能力，每个能力有输入、输出、边界、触发条件。Agent 负责选择和组合，不负责临场发明工具。

### 5.10 报告可信度显式展示

代表项目：`uzi-skill`、`ai-berkshire`、`deepear`、`x2t`

报告不只给结论，还要显示数据质量、引用、信号评分、信源历史表现、冲突观点、置信度和失败路径。

## 7. 不建议照搬的东西

| 反模式 | 风险 | 替代做法 |
|---|---|---|
| 先做自动实盘交易 | 权限、风控、合规、责任边界不清 | `paper_only`、suggestion pool、人工确认、审计日志 |
| 先上复杂多 Agent 状态机 | 成本高、调试难、收益不确定 | 单 Agent / Moderator 起步，流程稳定后再 LangGraph |
| 让 Agent 自由拼 HTTP 请求 | 无 provenance、认证边界混乱、难审计 | JSON CLI、Skill Gateway、Agent Gateway、MCP 工具目录 |
| 无数据契约就做 UI | UI 绑定隐式字段，后续难维护 | 先定义 DATA_CONTRACTS、schema version、source/fetched_at |
| MCP 直接暴露高风险动作 | 工具发现容易扩大权限面 | 只读 MCP 起步，高风险动作走 scoped Gateway |
| 报告只有自然语言结论 | 无法追溯、无法复核、无法比较 | 引用、数据质量、claim-to-source、信号评分、失败原因 |

## 8. 建议的第一阶段组合

如果要从这些项目中提炼一个稳妥的第一阶段建设方案，建议组合如下：

| 层 | 建议来源 | 第一阶段形态 |
|---|---|---|
| 数据 | `daily-stock-data` + `hhxg-market` + `tickflow-stock-panel` | CSV/static JSON/Parquet 契约，先稳定盘后数据和样例数据 |
| 工具 | `snowball-cli` + `privora-python-examples` + `quant-buddy-skill` | JSON CLI 和 Skill Gateway envelope，记录 session/version/scope |
| 策略 | `alphaagent` + `qlib` + `tickflow-stock-panel` | Factor DSL、SignalRecord、StrategyDef、基础回测 |
| 组合/风控 | `pyportfolioopt` + `lean` + `pa-agent` | TargetWeight、风险复算、审批票据、paper-only 状态机 |
| Agent | `jcp` + `tradingagents-family` + `panwatch` | Moderator、结构化中间态、预算和冷却 |
| 审计 | `quantdinger` + `ai-berkshire` + `x2t` | scope/audit、财务校验、信源/观点结算 |
| UI | `openashare` + `tickflow-stock-panel` | 工作台首页、运行流、个股页、盯盘页、报告页 |

第一阶段的目标不是复制某个完整项目，而是落下最小可复用骨架：数据契约、工具 envelope、静态快照、StrategyDef、run/session 记录、报告可信度展示。

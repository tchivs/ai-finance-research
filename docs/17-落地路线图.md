# 落地路线图 — 从资料库到当前项目执行计划

> 面向 HermesAlpha 与 ashare-audit 的可执行收敛稿。目标不是再总结一遍 42 个项目，而是把它们压成能排期、能验收、能被审计的建设路线。

## 0. 使用边界与执行前提

这是一份目标架构路线，不代表两个项目当前已经具备文中列出的模块。进入实施前，先用实际代码、数据和运行环境确认基线，再把每个阶段拆成项目内任务。

### 执行前提

| 前提 | 未满足时的处理 |
|------|----------------|
| 已明确目标用户和首个高频工作流 | 暂停扩展页面和 Agent 角色，先确定一个端到端场景 |
| 能取得至少一个稳定、合法的数据源 | 先做样例数据契约和离线快照，不承诺实时能力 |
| 已区分公开数据、认证数据和敏感数据 | 默认只接公开只读接口，认证能力延后 |
| 已确定运行形态：本地单用户或服务端多用户 | 未确定前不引入复杂权限和多租户设计 |
| 有可重复的验证环境 | 每阶段先补最小测试数据、失败样例和验收命令 |

### 非目标

- 本路线不提供投资建议，也不以策略收益率作为第一阶段成功标准。
- 第一阶段不自动执行实盘交易，不代用户完成第三方账号登录。
- 不要求一次性迁移所有数据源、Agent、页面或历史文档。
- 不因上游项目采用某项技术，就默认当前项目必须使用同一框架。

### 阶段门禁

```text
数据契约可验证
    -> 工具调用可记录和重放
        -> Agent 过程可追溯
            -> UI 能展示状态与证据
                -> 才评估自动化和高风险动作
```

上一个门禁未通过时，不以增加 Agent、页面或数据源数量代替基础问题修复。

## 1. 总体判断

42 个项目给出的共同结论是：金融 AI 系统不要从“一个全能 Agent”开始，而要从清晰边界开始。

```text
数据底座
    -> 文件/表/静态快照/工具输出都要有契约

工具层
    -> MCP / CLI / Agent Gateway / Skill Gateway / SKILL.md 都要可审计

Agent 层
    -> Moderator / 多角色 / BaseAgent 生命周期要有状态和门控

产品层
    -> 工作台、盯盘、报告、运行页要让用户看到过程和可信度

审计层
    -> response shape、session、version、scope、cache、date、source 都要留痕
```

优先顺序应是：先把数据和工具调用边界定住，再做 Agent 编排，再做 UI 产品化。反过来会导致漂亮前端和复杂 Agent 都建在不稳定的数据/工具地基上。

## 2. HermesAlpha 落地路线

HermesAlpha 的目标可以收敛为：本地优先的 A 股/多市场研究工作台，具备数据快照、Agent 会议室、盯盘提醒、报告生成和工具化外部数据接入。

### 2.1 目标形态

```text
HermesAlpha
    ├── Data Foundation
    │   ├── local market cache / snapshots
    │   ├── static daily snapshot
    │   ├── external provider CLI/gateway adapters
    │   └── data contracts
    │
    ├── Skill & Tool Layer
    │   ├── market-data skill
    │   ├── finance-search skill
    │   ├── sentiment/forecast/report skills
    │   ├── snowball-style JSON CLI adapters
    │   └── Privora-style skill gateway adapters
    │
    ├── Agent Layer
    │   ├── Moderator meeting room
    │   ├── BaseAgent collect/analyze/notify lifecycle
    │   ├── TradingAgents productized adapter
    │   └── run/session state
    │
    ├── Watch & Portfolio Layer
    │   ├── watchlist
    │   ├── alert_rules / alert_history
    │   ├── suggestion_pool
    │   └── portfolio context / PnL snapshot
    │
    └── UI Layer
        ├── workbench home
        ├── stock cockpit
        ├── report page
        ├── watch page
        ├── run timeline
        └── provider/tool settings
```

### 2.2 Phase H1 — 数据和工具边界先行

| 任务 | 来源 | 验收标准 |
|------|------|----------|
| 建立 `DATA_CONTRACTS.md`，定义行情、快照、报告、工具调用 envelope | daily_stock_data / UZI / Privora | 每个表/JSON/工具输出有字段、主键、时间语义、缺失值语义 |
| 建立静态日报快照接口：市场状态、两融、日历、快讯先用 JSON 文件 | hhxg-market | 每份快照包含 `date/schema_version/generated_at/from_cache/source` |
| 外部数据源先 CLI/gateway 化，不直接散落 HTTP 请求 | snowball-cli / Privora | 每次调用能记录 `command` 或 `skillId + params` 与 raw response hash |
| 高风险 Agent API 采用 scope/audit/idempotency/paper-only 组合 | QuantDinger | 每个 token 有 R/W/B/N/C/T、allowlist、rate limit，高风险动作默认 paper |
| Provider 设置页或诊断命令区分 public/auth/token/scope 状态 | snowball-cli / Privora | 用户能看到哪些接口免登录，哪些需要 token，token 是否有效 |

建议先不要做大规模实时行情服务。盘后快照和外部工具调用边界更容易稳定，也能快速给 Agent 和 UI 提供输入。

### 2.3 Phase H2 — Agent 能力拆包

| 任务 | 来源 | 验收标准 |
|------|------|----------|
| 拆出 `market-data`、`finance-search`、`sentiment`、`forecast`、`report` 五类 skill | Awesome Finance Skills | 每个 skill 有 `SKILL.md`、输入输出示例、测试/验证命令 |
| 搜索和引用进入本地 SQLite memory | Awesome Finance Skills | 有 `search_cache/search_detail/citation_key`，报告能回链来源 |
| 预测拆成 base forecast 与 Agent adjustment | Awesome / Kronos/FinCast | 报告同时保存模型原始预测、调整理由、使用的新闻/信号 |
| Report pipeline 拆成 cluster → section write → assemble → references | Awesome / UZI | 报告结构化输出，能渲染 Markdown/HTML，引用完整 |

这里的目标不是马上实现最强模型，而是先让能力边界稳定：工具做确定性工作，Agent 做判断和综合。

### 2.4 Phase H3 — Moderator 会议室与持仓上下文

| 任务 | 来源 | 验收标准 |
|------|------|----------|
| 引入 Moderator：先判断问题意图、选专家、分配任务 | JCP | 每次分析保存 `intent/expert_list/task_map` |
| 专家串行讨论，后续专家能看到前序发言和股票记忆 | JCP | 运行记录里能追溯每位专家输入、输出和引用记忆 |
| 加入持仓上下文和组合约束 | PanWatch / Privora | 同一股票在有/无持仓时上下文不同，建议能说明组合影响 |
| 建立 suggestion pool，不让 AI 建议直接变交易 | PanWatch | 建议状态包含 `proposed/accepted/rejected/expired`，有权重约束 |

这一步决定 HermesAlpha 是否从“问答工具”变成“研究工作台”。关键不是专家数量，而是 Moderator 的任务拆分和上下文可追溯。

### 2.5 Phase H4 — 盯盘和提醒闭环

| 任务 | 来源 | 验收标准 |
|------|------|----------|
| 建立 `watchlist/alert_rules/alert_history/quote_cache` | magpie / PanWatch | 规则、触发、冷却、历史全部落库 |
| 支持价格规则和组合规则：gte/lte/breakout/breakdown/AND/OR/composite | magpie / PanWatch | 每条规则能解释触发原因和关联数据 |
| 自动触发加入 budget/cooldown/enable gate | PanWatch | 无预算/冷却中/未启用时有明确状态，不静默失败 |
| 增加 synthetic `test-fire` | magpie | 用户能测试通知链路，不需要等真实行情触发 |

盯盘不是 cron 跑报告。验收重点是触发可解释、重复可抑制、历史可追溯、通知可测试。

### 2.6 Phase H5 — UI 工作台

| 页面 | 必须有 | 来源 |
|------|--------|------|
| 首页 | 市场状态、快照日期、待看信号、运行中任务、最近报告 | OpenAshare / tickflow / hhxg |
| 个股页 | K 线、新闻、资金、持仓、策略、Agent 会议入口 | tickflow / JCP / trade-skills |
| 报告页 | 数据质量 Banner、证据卡、多空冲突、引用回链 | UZI / Awesome |
| 盯盘页 | 规则、触发历史、冷却、预算、test-fire、digest | PanWatch / magpie |
| 运行页 | Timeline、工具调用、参数、job progress、raw response、失败重试 | Vibe-Trading / QuantDinger / Privora / quant-buddy |
| 设置页 | Provider public/auth、token/scope、paper_only、模型成本、能力检测 | snowball / QuantDinger / Privora / Agent-Reach |

第一版 UI 不要做营销首页。金融工作台第一屏要回答：今天有什么状态、什么信号、什么任务、什么风险、下一步点哪里。

## 3. ashare-audit 落地路线

ashare-audit 的目标应收敛为：金融数据、策略、Agent 输出和工具调用的审计系统。它不应该只审计最终报告文本，而要审计数据来源、工具 envelope、策略代码、静态快照、模型/Agent 调整和 UI 可解释性。

### 3.1 目标形态

```text
ashare-audit
    ├── Input Audit
    │   ├── data contracts
    │   ├── provider/source/fetched_at
    │   ├── snapshot date/schema/cache
    │   └── raw payload hash
    │
    ├── Tool Audit
    │   ├── command / skillId
    │   ├── params / session / version
    │   ├── response shape
    │   ├── scope / token boundary
    │   └── sensitive data flags
    │
    ├── Strategy Audit
    │   ├── AST lint
    │   ├── future function check
    │   ├── trading cost check
    │   ├── formula parameter freeze
    │   └── TopN/order validation
    │
    ├── Report Audit
    │   ├── citation completeness
    │   ├── base vs adjusted forecast
    │   ├── claim-to-source mapping
    │   └── data quality banner
    │
    └── Audit UI
        ├── run flow
        ├── issues and fixes
        ├── raw evidence
        └── regression checklist
```

### 3.2 Phase A1 — Tool Envelope 审计底座

| 任务 | 来源 | 验收标准 |
|------|------|----------|
| 定义统一 `ToolCallEnvelope` | Privora / quant-buddy / snowball | 包含 tool/command、params、session、version、auth、response_shape、raw_hash |
| 定义 Agent scope audit 字段 | QuantDinger | 包含 token_id/name、scope_class、market/instrument allowlist、paper_only、rate_limit、status_code |
| 对 CLI/gateway/MCP/skill 调用做统一记录 | snowball / Privora / joinquant / quant-buddy | 最终报告能追溯到每次工具调用，不只追溯到自然语言 |
| response shape 校验 | Privora | `data` 是 array 还是 object、pagination 在哪里都可验证 |
| session/version 审计 | quant-buddy | 新任务不能复用旧 session，版本不匹配要阻断或提示升级 |

这是 ashare-audit 最应该优先做的能力。没有 tool envelope，后面的报告审计只能停留在文本层。

### 3.3 Phase A2 — 数据质量和快照审计

| 任务 | 来源 | 验收标准 |
|------|------|----------|
| 数据质量 gate：必填字段、空字段、单位、时间语义 | UZI / daily_stock_data | 缺关键字段时阻断，非关键字段 warning |
| 静态快照检查：`date/schema_version/from_cache/generated_at` | hhxg-market | 非交易日或缓存数据必须在审计结果中显式提示 |
| provider/source health | Agentic China Data / TDX / a-stock-data | 每个字段能标注来源、延迟、降级状态 |
| 原始 payload hash 和引用 key | Awesome / snowball | 关键结论能回链 raw payload 或 citation key |

### 3.4 Phase A3 — 策略和公式审计

| 任务 | 来源 | 验收标准 |
|------|------|----------|
| 聚宽策略 AST lint | joinquant-skill | 检查未来函数、非法 API、交易成本、settings 缺失 |
| 公式执行参数冻结 | quant-buddy | 筛选条件、时间窗口、排序字段、TopN 都写入审计记录 |
| StrategyDef 审计 | tickflow | 选股/监控/回测是否复用同一份策略定义 |
| Agent 策略沙箱审计 | QuantDinger | 指标/脚本是否经过 contract、safe_exec、validate、paper-only 闸门 |
| 回测约束审计 | tickflow / daily_stock_analysis | T+1、涨跌停、停牌、手续费、滑点、仓位上限有无纳入 |

策略审计的目标不是判断策略赚不赚钱，而是判断它有没有偷看未来、口径有没有漂移、结果是否可复现。

### 3.5 Phase A4 — 报告和 Agent 输出审计

| 任务 | 来源 | 验收标准 |
|------|------|----------|
| claim-to-source mapping | UZI / Awesome | 每个关键数字和判断都有来源或明确标注为观点 |
| base forecast vs adjusted forecast 审计 | Awesome / Kronos | 预测调整必须保留调整理由和输入信号 |
| Moderator/多 Agent 过程审计 | JCP / TradingAgents | 能看到专家选择、任务、发言、冲突和总结来源 |
| 数据质量 Banner 输出 | UZI / hhxg | 报告顶部显示缺失、降级、缓存、最近交易日 |

### 3.6 Phase A5 — 审计 UI

| 页面 | 必须有 | 来源 |
|------|--------|------|
| 审计运行页 | RunFlow、节点状态、失败重试、产物链接 | daily_stock_analysis / Vibe |
| 工具调用页 | command/skillId、参数、版本、response shape、raw JSON | Privora / quant-buddy |
| 数据质量页 | 字段来源、降级状态、快照日期、cache 状态 | UZI / hhxg / a-stock-data |
| 策略审计页 | AST lint issue、未来函数、交易成本、TopN 排序 | joinquant / quant-buddy |
| 报告审计页 | claim、source、confidence、issue、suggested fix | UZI / ai-berkshire |

## 4. 共同基础设施

HermesAlpha 和 ashare-audit 不应各自重复造轮子。建议共享以下基础设施：

| 共享模块 | 用途 | 受益项目 |
|----------|------|----------|
| `ToolCallEnvelope` schema | 统一工具调用留痕 | HermesAlpha / ashare-audit |
| AgentGateway scope/audit schema | 统一 Agent token、scope、idempotency 和 paper-only 高风险边界 | HermesAlpha / ashare-audit |
| `DataContract` schema | 表、JSON、快照、工具输出契约 | 两者 |
| Provider health / Doctor | 检测数据源、LLM、通知、token | 两者 |
| static snapshot format | 日报、两融、日历、快讯 | 两者 |
| citation/reference store | 搜索结果、新闻、报告引用 | 两者 |
| alert rule schema | 盯盘和审计规则共用 | 两者 |
| run directory / run state | 长任务产物和日志 | 两者 |

## 5. 第一阶段建议排期

### 第 1 周：契约和 envelope

| 交付 | 验收 |
|------|------|
| `DATA_CONTRACTS.md` 初版 | 至少覆盖行情、快照、工具调用、报告引用 |
| `ToolCallEnvelope` 初版 | CLI/gateway/skill 都能映射进去 |
| `static_snapshot.json` 样例 | 包含 date/schema/generated_at/source/cache |
| `/doctor` 或诊断脚本 | 能检查 provider、token、LLM、通知配置 |

### 第 2 周：最小数据和审计闭环

| 交付 | 验收 |
|------|------|
| 一个外部数据 CLI adapter | 能记录 command、raw response、认证状态 |
| 一个 gateway adapter | 能记录 skillId、scope、response shape |
| 一个快照读取器 | 能提示最近交易日和 cache 状态 |
| 一个审计报告样例 | 能列出数据缺口、工具调用、来源引用 |

### 第 3 周：Agent 和 UI 最小闭环

| 交付 | 验收 |
|------|------|
| HermesAlpha Moderator 原型 | 保存 intent、expert_list、task_map、专家发言 |
| watchlist/alert_rules/alert_history | 支持一条规则 test-fire |
| ashare-audit 工具调用页草图/文档 | 展示 command/skillId、params、response shape |
| 数据质量 Banner | 报告顶部能显示缺失/降级/cache/date |

## 6. 明确暂缓事项

这些事情有价值，但不应排在第一阶段：

| 暂缓项 | 原因 |
|--------|------|
| 完整多市场交易执行 | 数据和审计边界未稳前风险高 |
| 大规模实时行情服务 | 先用静态快照和本地缓存证明口径 |
| 复杂 LangGraph 全状态机 | 先用 Moderator + run state 足够验证产品路径 |
| 自动实盘交易 | 建议池和模拟盘先行，真实交易需更强风控和合规 |
| 大而全 UI | 先做首页、个股页、运行页、盯盘页、工具调用页 |

## 7. 成功标准

第一轮落地成功，不看功能数量，看这 8 个问题是否能回答：

1. 这个结论用了哪些数据源？
2. 哪些字段来自缓存、降级源或最近交易日？
3. 每次工具调用的参数、版本、认证状态和响应形态是什么？
4. Agent 为什么选择这些专家或工具？
5. AI 预测的 base result 和 adjusted result 是否分开保存？
6. 盯盘提醒为什么触发，为什么没有重复触发？
7. 报告里的关键数字能否回到 raw payload 或 citation？
8. 用户不用翻日志，能否从 UI 看到运行进度、失败原因和下一步操作？

能回答这些问题，系统就已经从“AI demo”进入“可维护金融工具”的轨道。

## 8. 阶段交付记录模板

每个阶段结束时，用同一格式记录实际交付，避免路线图只保留计划、不反映结果。

```markdown
## <阶段编号与名称>

- 状态：未开始 / 进行中 / 阻塞 / 已完成 / 已取消
- 负责人：<owner>
- 基线：<开始时已有能力>
- 交付物：<文档、schema、接口、页面或测试>
- 验收证据：<命令、截图、样例产物或测试报告>
- 未解决风险：<风险及影响>
- 关键决策：<链接到决策记录>
- 下一阶段门禁：<必须满足的条件>
```

状态只根据验收证据更新，不以“代码已写完”代替端到端验证。路线变化时保留取消原因和替代方案，便于后续复盘。
